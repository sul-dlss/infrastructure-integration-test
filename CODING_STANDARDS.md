# Coding standards

These apply to everyone who changes this repo, people and coding agents alike.

## Keep spec dependency information current

Many specs depend on earlier specs: on test data those specs save, or on the state they leave an object in.
See "Test type and order" in the README. This information lives in two places:

- `spec/spec_dependencies.yml` is maintained by hand. It records what can't be derived from the code:
  - state dependencies
  - specs that can't be replayed

  The comment at the top of the file explains its purpose.
- `spec_dependencies.md` is generated by `bin/spec_deps` from the spec code and that YAML file.

When a change might affect either one, do these in the same change:

1. **Review `spec/spec_dependencies.yml` against its stated purpose and update it.** Changes that need this:
   - A spec now relies on an object being in a state that an earlier spec produces: accessioned,
     at a particular version, or with particular files. If so, add a `state_dependencies` entry.
   - A spec can no longer be run twice against the same data. If so, add a `not_replayable` entry.
     Remove entries that no longer hold.
   - A spec is renamed, moved or deleted. `bin/spec_deps` fails on paths that don't exist.
2. **Regenerate the doc with `bin/spec_deps --write`.** Changes that need this:
   - adding, removing, renaming or moving a spec
   - changing a `save_test_data` / `load_test_data` call or a `spec_name`
   - changing a spec's `type:` or `if:` metadata
   - changing the shared examples in `spec/support/shared_examples/`
3. **Check the result with `bin/spec_deps --check`, and read the generated doc.**
   - "Keys loaded but never written" usually means a typo or a missing writer.
   - "Analysis warnings" means the script couldn't follow some code. Pass data keys as string literals,
     or through `let(:spec_name)`, so the script can resolve them.

Don't edit `spec_dependencies.md` by hand. Your edits will be overwritten the next time the doc is generated.
