# Coding standards

These apply to everyone who changes this repo, people and coding agents alike.

## Keep spec dependency information current

Many specs depend on earlier specs: on test data those specs save, or on the state they leave an object in.
See "Test type and order" in the README. This information lives in two places:

- `spec/spec_dependencies.yml` is maintained by hand. It records what can't be derived from the code:
  - state dependencies
  - specs that can't be replayed

  The comment at the top of the file explains its purpose.
- `spec_dependencies.md` is generated by `bin/spec_deps` from the spec code and that YAML file.

When a change might affect either one, do these in the same change:

1. **Review `spec/spec_dependencies.yml` against its stated purpose and update it.** Changes that need this:
   - A spec now relies on an object being in a state that an earlier spec produces: accessioned,
     at a particular version, or with particular files. If so, add a `state_dependencies` entry.
   - A spec can no longer be run twice against the same data. If so, add a `not_replayable` entry.
     Remove entries that no longer hold.
   - A spec is renamed, moved or deleted. `bin/spec_deps` fails on paths that don't exist.
2. **Regenerate the doc with `bin/spec_deps --write`.** Changes that need this:
   - adding, removing, renaming or moving a spec
   - changing a `save_test_data` / `load_test_data` call or a `spec_name`
   - changing a spec's `type:` or `if:` metadata
   - changing the shared examples in `spec/support/shared_examples/`
3. **Check the result with `bin/spec_deps --check`, and read the generated doc.**
   - "Keys loaded but never written" usually means a typo or a missing writer.
   - "Analysis warnings" means the script couldn't follow some code. Pass data keys as string literals,
     or through `let(:spec_name)`, so the script can resolve them.

Don't edit `spec_dependencies.md` by hand. Your edits will be overwritten the next time the doc is generated.

## Test the repo's own tooling in `tool_spec/`

Code in `lib/`, such as `lib/spec_deps.rb` behind `bin/spec_deps`, has unit tests in `tool_spec/`.
Run them with:

```
bin/rspec -O tool_spec/.rspec
```

The `-O` option matters. It replaces the project `.rspec`, so the integration suite's `spec/spec_helper.rb`
never loads. Keep these tests out of `spec/`: its global ordering silently drops examples that have
no `type:`, and loading it starts the browser setup.

When you change `lib/spec_deps.rb`, add or update a test in the same change. CI runs these tests,
and `bin/spec_deps --check`, in the `tool-spec` job (`.circleci/config.yml`).

### Fixtures: small, made-up trees

Each test builds the small repo tree it analyzes inline, using `build_tree` / `graph_for` in
`tool_spec/tool_spec_helper.rb`. These trees are made up and only a few files each, so a failing
test points at the one rule that broke. Don't point tests at the real `spec/` directory or at a
pinned commit from this repo's history. Those trees are large, they change for unrelated reasons,
and when a test fails it's hard to tell which rule broke.

**When `bin/spec_deps` mishandles a pattern found in a real spec, copy a trimmed excerpt of that
spec into a new fixture.** Keep only the lines that matter: the `describe`, the `let`s, and the
`save_test_data` / `load_test_data` calls. Then write the test, and fix the code until it passes. That way
the fixtures pick up real-world patterns as they appear, without depending on the real suite.

The real suite is still checked: `bin/spec_deps --check` runs the parser over the current specs.
It fails if the parser breaks on them or if `spec_dependencies.md` is out of date.

### The golden doc

`tool_spec/spec_deps/doc_spec.rb` compares the rendered doc for a sample tree with
`tool_spec/fixtures/sample_doc.md`. After an intended change to the doc's format, regenerate the golden copy
and review its diff:

```
UPDATE_GOLDEN=1 bin/rspec -O tool_spec/.rspec tool_spec/spec_deps/doc_spec.rb
```
